# spec_MILEAGE — спецификация: учёт пробега авто в решении по заявке

ID задачи: `MILEAGE`. Основа: `docs/intent/intent_MILEAGE.md` (интервью Grill Me — `grill_MILEAGE.md`).
Все бизнес-числа — см. `backend/config/rules.php`; в спеке и коде копий значений не храним.

## 1. Входит / не входит

### Входит
- Проверка пробега в расчёте решения: при пробеге ≥ 400 000 км LTV-`approve` понижается до `review`. — intent, разд. 3, п.1 (интервью, Вопрос 1)
- Правило «только понижает»: LTV-`review` и LTV-`reject` не перекрываются и не смягчаются («худшее из правил»). — intent, разд. 3, п.2 (интервью, Вопрос 2)
- Валидация: заявка без пробега (отсутствующее поле / null / пустая строка) невалидна, ответ 422. — intent, разд. 3, п.4 (интервью, Вопрос 3)
- Код причины у каждого решения (LTV-обоснования approve/review/reject + высокий пробег); причина возвращается в API-ответе и хранится в БД. — intent, разд. 3, п.5–6 (интервью, Вопросы 4–5)
- Значение 400 000 км выносится в `backend/config/rules.php` (сегодня его там нет). — следствие конвенции AGENTS.md «бизнес-числа — из rules.php»

### Не входит
- Фронтенд: форма заявки не меняется, причина решения на ней не показывается. — intent, разд. 5 (интервью, Вопрос 6)
- Задача LOAN-12 (лимит по возрасту авто) — отдельная, не делается. — intent, разд. 5
- Изменение существующего жёсткого потолка пробега при валидации (`vehicle.max_mileage_km` = 500 000, `rules.php`) — не меняется в этой задаче (см. Open questions, ОО-3).
- Пересчёт решений уже сохранённых заявок — не делается (см. Open questions, ОО-4).

## 2. Требования и критерии приёмки

### REQ-MILEAGE-01 — порог высокого пробега
При пробеге ≥ 400 000 км заявка с LTV-`approve` получает решение `review`.
Число 400 000 — интервью, Вопрос 1; должно попасть в `rules.php` после закрытия ОО-5 (согласование риск-менеджментом).
Примечание: граница включительная (400 000 → уже `review`), но финальная формулировка — см. ОО-1.

**AC-MILEAGE-01** (граничные значения, LTV-`approve` по порогам `rules.php`):
| Пробег, км | Ожидаемое решение | Код причины |
|---|---|---|
| 399 999 | `approve` | LTV-обоснование approve |
| 400 000 | `review` | высокий пробег |
| 400 001 | `review` | высокий пробег |
Источник чисел: 399 999/400 000/400 001 — границы из интервью (Вопрос 1); 400 001 < потолка валидации 500 000 (`rules.php`, `vehicle.max_mileage_km`), поэтому заявка валидна.

### REQ-MILEAGE-02 — правило только понижает
Пробег ≥ 400 000 км понижает только `approve` → `review`. LTV-`review` остаётся `review`, LTV-`reject` остаётся `reject` («худшее из правил»). — intent, разд. 3, п.2 (интервью, Вопрос 2)

**AC-MILEAGE-02**:
- пробег 400 000 + LTV-`review` → `review` (пороги LTV — см. `rules.php`)
- пробег 400 000 + LTV-`reject` → `reject`
- пробег 399 999 + LTV-`review` → `review`; + LTV-`reject` → `reject` (решение по LTV без изменений)

### REQ-MILEAGE-03 — заявка без пробега невалидна
Заявка без пробега (поле отсутствует, null или пустая строка) отклоняется с HTTP 422 до расчёта решения. — intent, разд. 3, п.4 (интервью, Вопрос 3)
Изменение против текущего кода: пустая строка сегодня считается нулевым пробегом (`backend/src/Domain/ApplicationValidator.php`); после изменения — 422. Код статуса невалидной заявки — `backend/src/Http/ApplicationController.php`.

**AC-MILEAGE-03**:
- поле `mileage` отсутствует → 422, решение не считается
- `mileage` = null → 422
- `mileage` = `""` (пустая строка) → 422 (регрессия относительно текущего поведения — раньше 0)

### REQ-MILEAGE-04 — код причины у каждого решения
Каждое решение сопровождается кодом причины: LTV-обоснование (approve / review / reject) или высокий пробег. Причина возвращается в API-ответе и хранится в БД. — intent, разд. 3, п.5–6 (интервью, Вопросы 4–5)

**AC-MILEAGE-04**:
- LTV-`approve` без высокого пробега (399 999) → код причины LTV-approve, есть в API-ответе и в записи БД
- пробег 400 000 + LTV-`approve` → `review`, код причины «высокий пробег», есть в API-ответе и в БД
- LTV-`review` / LTV-`reject` → соответствующий LTV-код причины

### REQ-MILEAGE-05 — потолок валидации не меняется
Существующий жёсткий потолок пробега при валидации (`vehicle.max_mileage_km` = 500 000, `rules.php`) остаётся без изменений: заявки с пробегом выше потолка отклоняются до расчёта решения. — intent, разд. 3, п.7; неизменность — Open question ОО-3 (не решено в интервью, спека фиксирует «не меняется» до решения)

**AC-MILEAGE-05**: пробег 500 001 → отклонение до расчёта решения (поведение как сегодня).

## 3. Open questions (перенесены из intent, разд. 4)

Все вопросы из intent остаются открытыми — ни один не закрыт этой спекой; спека фиксирует рабочие формулировки из ответов интервью до подтверждения заказчиком/риск-менеджментом.

- **ОО-1.** Граница «не больше 400 000 км»: исходная формулировка задачи допускает ровно 400 000, интервью — «400 000 → уже review» (Вопрос 1). Спека исходит из ответа интервью (включительная граница). Требует подтверждения заказчиком; при ином решении — корректировка REQ/AC-01 и `plan_MILEAGE.md`.
- **ОО-2.** «Иначе решение review»: буквальное прочтение ставит `review` при любом решении, интервью — только понижение `approve` → `review` с сохранением `reject` (Вопрос 2). Спека следует интервью (REQ-MILEAGE-02). Требует подтверждения.
- **ОО-3.** Жёсткий потолок пробега при валидации (500 000, `rules.php`) остаётся без изменений? В интервью не решалось. Спека фиксирует «не меняется» (REQ-MILEAGE-05) до решения риск-менеджмента.
- **ОО-4.** Уже сохранённые заявки: пересчитывать ли их решения и чем заполнять код причины у старых записей? Не закрыто; спека выносит пересчёт за рамки задачи (см. «Не входит»). Требует решения заказчика.
- **ОО-5.** Ссылка на согласование числа 400 000 риск-менеджментом (тикет): в интервью не прозвучала. Число не вносится в `rules.php` до появления согласования (AGENTS.md: смена порога — только по явному решению риск-менеджмента).
- **ОО-6 (новый, обнаружен при составлении спеки; не добавляет требований из intent):** какой код причины у заявки, где одновременно действует и LTV-`review`, и высокий пробег — intent и интервью приоритет кодов не задают (REQ-MILEAGE-04 требует «код у каждого решения», но не приоритет). Требует решения при планировании.
