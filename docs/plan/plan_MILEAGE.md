# plan_MILEAGE — проверка пробега в решении по заявке

ID задачи: `MILEAGE`. Постановка: «пробег авто не больше 400 000 км, иначе решение
`review`». Число 400 000 берётся из постановки задачи; после реализации оно живёт
только в `backend/config/rules.php` и нигде больше не дублируется (AGENTS.md).

Сверка с картой кода: `docs/setup/code_map.md` в репозитории **отсутствует**
(задание 1.2.2 не выполнено). Точки, где участвует пробег, взяты из отчёта scout
(`docs/setup/agents.md`) и проверены прямым разбором кода. Полный список вызовов
`DecisionEngine` / `decide()` приведён ниже и исчерпывающий.

## Как устроено сейчас (контекст для реализатора)

- Валидация — `ApplicationValidator`: пробег жёстко ограничен `0..vehicle.max_mileage_km`
  (значение — см. rules.php); нарушение → `ValidationException` → HTTP 422, до решения
  заявка не доходит. Пробег `''` нормализуется в 0, отсутствующий ключ/null → −1 → 422.
- Решение — `DecisionEngine::decide(float $ltv)`: только LTV-пороги, значения из
  `rules.php` (`ltv.approve_max` / `ltv.review_max`).
- Оркестрация — `AssessmentService::assess()`: валидация → LTV → решение → лимит;
  `approved_limit` равен запрошенной сумме только при `approve`, иначе 0.
- `decide()` и конструктор `DecisionEngine` используются ровно в 4 местах:
  `backend/src/AppFactory.php:37`, `backend/src/Domain/AssessmentService.php:33`,
  `tests/Unit/DecisionEngineTest.php:17,23`, `tests/Unit/AssessmentServiceTest.php:27`.

## Дизайн решения

- Новый порог — отдельная секция rules.php `mileage.review_above_km`. Не в `vehicle`:
  это правило решения, а не валидации; жёсткий потолок `vehicle.max_mileage_km`
  остаётся без изменений.
- Правило встраивается в `DecisionEngine` — класс, единственная ответственность
  которого выдавать решение. `AssessmentService` остаётся оркестратором и лишь
  пробрасывает валидированный `$input['mileage']`. HTTP-слой, репозиторий и фронтенд
  не меняются: оба эндпоинта (`/api/ltv`, `/api/applications`) идут через `assess()`.
- Семантика — «худшее из правил»: сначала решение по LTV, затем понижение
  `approve` → `review` при пробеге выше порога. `review` и `reject` по LTV пробегом
  не смягчаются (допущение — см. Вопрос 1).
- Диапазоны после внедрения: `0..review_above_km` — решение по LTV;
  `review_above_km+1 .. max_mileage_km` — `review` при LTV-`approve`; выше
  `max_mileage_km` — 422 на валидации.
- Отклонённые альтернативы: проверка в `ApplicationValidator` (там жёсткий 422,
  а нужно `review`); в контроллере (бизнес-правило не в HTTP-слое); инлайном в
  `AssessmentService` (расщепляет логику решения между классами).

## 2. Шаги

1. `rules.php`: секция `mileage.review_above_km` + docblock. Значение — из постановки
   задачи `MILEAGE`; это и есть согласованное число (Вопрос 3 — про его статус).
2. `DecisionEngineTest` (красный): setUp на новую сигнатуру, пороги из rules.php;
   граничный data-provider (порог − 1 / ровно / + 1). Тесты красные — движок пока не умеет.
3. `DecisionEngine` (зелёный): новые сигнатуры конструктора и `decide()`; понижение
   `approve` → `review` при пробеге выше порога; обновить docblock. Юнит-тесты зелёные.
4. `AssessmentService` + `AppFactory` одним шагом: проброс `$input['mileage']` и порога
   из конфига. Иначе сломаны и сборка приложения, и `AssessmentServiceTest`. После шага —
   контрольный поиск `decide(` и `DecisionEngine(`: посторонних вызовов остаться не должно.
5. `AssessmentServiceTest`: сквозные кейсы понижения решения и обнуления лимита.
6. `ApplicationValidatorTest`: пустой/отсутствующий пробег и жёсткий потолок — фиксируют,
   что 422-слой поведением не изменился.
7. Проверка: `make lint`, `make test`, ручной смоук `POST /api/ltv` — `400000` → `approve`,
   `400001` → `review`, пробег за `max_mileage_km` → 422.

## 3. Тесты

Граничные значения в тестах берём из rules.php: `review_above_km − 1` / ровно / `+ 1`
(при текущем значении порога это 399999 / 400000 / 400001) — при смене порога тесты
следуют за конфигом, а не хранят копии чисел.

`tests/Unit/DecisionEngineTest.php` (LTV в зоне `approve`):
- пробег 399999 (порог − 1) → `approve` — правило не срабатывает;
- пробег 400000 (ровно порог) → `approve` — «не больше»: граница включительно;
- пробег 400001 (порог + 1) → `review` — понижение;
- пробег выше порога при LTV-`review` → `review` (без изменений);
- пробег выше порога при LTV-`reject` → `reject` (не смягчаем; допущение — Вопрос 1);
- существующие LTV-кейсы при пробеге ниже порога — решения не меняются;
- инвариант конфига: `mileage.review_above_km` ≤ `vehicle.max_mileage_km`, иначе новое
  правило недостижимо (диапазон между ними перехватывает валидация).

`tests/Unit/AssessmentServiceTest.php` (сквозные, реальные rules.php):
- LTV 50% и пробег 399999 → `approve`, `approved_limit` равен запрошенной сумме;
- LTV 50% и пробег 400000 → `approve`, `approved_limit` равен запрошенной сумме;
- LTV 50% и пробег 400001 → `review`, `approved_limit` = 0.

`tests/Unit/ApplicationValidatorTest.php` (слой валидации — до решения не доходит):
- пустой пробег: ключ `mileage` отсутствует (и отдельно null) → `ValidationException`
  с ключом `mileage` в errors;
- пробег `max_mileage_km + 1` → `ValidationException` — жёсткий потолок не сдвинулся.

Ручная проверка после `make up`: `POST /api/ltv` с `mileage: 400001` → `decision: review`;
с `mileage: 400000` → `approve`.

## 4. Риски

1. Существующая проверка `max_mileage_km` — теперь два правила о пробеге в разных слоях:
   жёсткая валидация (422) и мягкий порог понижения решения. Зона видимости нового
   правила — только `review_above_km+1 .. max_mileage_km`. Главный риск: если порог
   в rules.php станет больше `max_mileage_km`, правило молча станет недостижимым.
   Защита — инвариант-тест и docblock в rules.php; числа дублировать в коде/тестах нельзя.
2. Смена сигнатуры `decide()` и конструктора `DecisionEngine` ломает все точки
   использования — их ровно четыре, все в списке Файлов; менять только согласованно
   (шаги 2–4). Пропуск = фатальная ошибка в рантайме, а не в тестах.
3. Существующие тесты: fixture-пробег 84000/96000 ниже порога, ожидания не меняются,
   но конструкторы `DecisionEngine` в обоих тестовых файлах требуют обновления. Локальные
   копии LTV-порогов (60.0/85.0) в `DecisionEngineTest` шаг 2 заменяет чтением rules.php —
   это соответствует правилу «не хранить копии чисел конфига».
4. `approved_limit` при понижении обязан стать 0 — это уже даёт существующая строка
   `AssessmentService.php:39`, её менять не нужно. Риск «доработать» и выдать лимит
   при `review` — не дорабатывать.
5. Пустой пробег — «две пустоты»: отсутствующий ключ/null → 422 (норм), а пустая строка
   нормализуется в 0 км и может получить `approve`. Асимметрия существующая, фича её не
   трогает; если заказчик ждёт 422 на пустой строке — отдельное изменение (Вопрос 6).
6. Не входит (out of scope): фронтенд (`app.js` рендерит `decision` как есть, класс
   `decision--review` уже есть); БД — `schema.sql`/`seed.sql` (ENUM `decision` уже содержит
   `review`; максимальный пробег в seed ниже порога — существующие заявки правило не
   задевает, пересчёт старых решений не делаем); причина `review` в API-ответе и БД
   (Вопрос 5); `/health`; задача LOAN-12 (`ltv_by_age`); изменение `max_mileage_km` —
   без решения риск-менеджмента стоп (AGENTS.md); mock vin-сервиса (пробег справочника —
   данные CASE-08, не эта задача).
7. Документация: число 400 000 не дублировать в README, docs и комментариях кода —
   писать «см. rules.php» (AGENTS.md). Обновление README в задачу не входит.

## Вопросы, на которые без заказчика не ответить

1. Пробег выше 400 000 при LTV-`reject`: оставляем `reject` (план предполагает «худшее
   из правил») или требование «иначе решение review» выполняется буквально — даже
   `reject` заменяется на `review`?
2. «Не больше 400 000 км» — граница включительная: 400 000 ещё `approve`, 400 001 уже
   `review`? План исходит из этого.
3. Число 400 000 подтверждено риск-менеджментом (тикет/ссылка на согласование) как
   постоянное правило, или это учебное значение, которое после пилота могут менять?
4. Жёсткий потолок валидации `vehicle.max_mileage_km` (см. rules.php) остаётся без
   изменений: выше него — 422, а не `review`?
5. Нужно ли возвращать/хранить причину `review` (высокий пробег) для андеррайтера и
   фронтенда? Сейчас причина решения нигде не фиксируется, в скоуп это не входит.
6. Пустая строка в поле пробега сегодня превращается в 0 км и проходит валидацию —
   так и оставляем, или пустое значение должно давать 422?
7. Правило должно действовать на оба эндпоинта — `/api/ltv` и `/api/applications`?
   План: да, оба считают решение через `AssessmentService::assess()`.
