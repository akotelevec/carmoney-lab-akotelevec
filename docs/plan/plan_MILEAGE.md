# plan_MILEAGE — проверка пробега в решении по заявке

ID задачи: `MILEAGE`. Постановка: «пробег авто не больше 400 000 км, иначе решение
`review`». Число 400 000 берётся из интервью (см. `docs/intent/intent_MILEAGE.md`,
Вопрос 1); после реализации оно живёт только в `backend/config/rules.php` и нигде
больше не дублируется (AGENTS.md).

Версия плана: v2 — сверен со спекой `docs/spec/spec_MILEAGE.md` (ДЗ.1) и дополнен.
Сверка с картой кода: `docs/setup/code_map.md` в репозитории **отсутствует**
(задание 1.2.2 не выполнено; перепроверено перед этой версией плана). Точки, где
участвует пробег и решение, взяты из отчёта scout (`docs/setup/agents.md`) и
проверены прямым разбором кода. Список вызовов `DecisionEngine` / `decide()`
приведён ниже и исчерпывающий.

## Как устроено сейчас (контекст для реализатора)

- Валидация — `ApplicationValidator`: пробег жёстко ограничен `0..vehicle.max_mileage_km`
  (значение — см. rules.php); нарушение → `ValidationException` → HTTP 422, до решения
  заявка не доходит. Отсутствующий ключ/null → −1 → 422; **пустая строка
  нормализуется в 0** (`(int) ''`) и проходит — по REQ-MILEAGE-03 это меняется.
- Решение — `DecisionEngine::decide(float $ltv)`: только LTV-пороги, значения из
  `rules.php` (`ltv.approve_max` / `ltv.review_max`). Кода причины нет нигде:
  движок его не выдаёт, `assess()` не возвращает, API-ответ не содержит,
  в `decisions` нет столбца.
- Оркестрация — `AssessmentService::assess()`: валидация → LTV → решение → лимит;
  `approved_limit` равен запрошенной сумме только при `approve`, иначе 0.
- Сохранение — `ApplicationRepository::save()` пишет заявку, авто и решение
  (`decisions`: ltv, decision, approved_limit); `find()`/`listApplications()`
  отдают решение в SELECT.
- `decide()` и конструктор `DecisionEngine` используются ровно в 4 местах:
  `backend/src/AppFactory.php:37`, `backend/src/Domain/AssessmentService.php:33`,
  `tests/Unit/DecisionEngineTest.php:17`, `tests/Unit/AssessmentServiceTest.php:27`.
- Схема БД (`db/schema.sql`) применяется только при первом старте пустого тома
  (`docker-entrypoint-initdb.d`); механизма миграций в проекте нет. `make seed`
  льёт только данные, `scripts/reset_db.sh` запускать нельзя (AGENTS.md) —
  для живой БД нужен ALTER-файл (см. Файлы). Feature-тестов в репозитории нет
  (только `tests/Unit/`) — HTTP-часть AC закрывается смоуком.

## Дизайн решения

- Порог — отдельная секция rules.php `'mileage' => ['review_from_km' => …]`.
  Имя `review_from_km` (не `review_above_km`): граница включительная, «от этого
  значения». Не в секции `vehicle`: это правило решения, а не валидации; жёсткий
  потолок `vehicle.max_mileage_km` остаётся без изменений (REQ-MILEAGE-05).
- Правило встраивается в `DecisionEngine` — класс, единственная ответственность
  которого выдавать решение. `AssessmentService` остаётся оркестратором: пробрасывает
  валидированный `$input['mileage']` и причину из результата. HTTP-слой, репозиторий
  и фронтенд не содержат логики решения: оба эндпоинта (`/api/ltv`,
  `/api/applications`) идут через `assess()`.
- Семантика — «худшее из правил» (REQ-MILEAGE-02): сначала решение по LTV, затем
  понижение `approve` → `review` при пробеге на пороге и выше; `review` и `reject`
  по LTV пробегом не смягчаются и не перекрываются.
- Диапазоны после внедрения: `0 .. review_from_km − 1` — решение по LTV;
  `review_from_km .. max_mileage_km` — `review` при LTV-`approve`; выше
  `max_mileage_km` — 422 на валидации.
- Код причины (REQ-MILEAGE-04) — движок возвращает DTO `Decision`
  (`decision` + `reason`), а не голую строку. Коды причин — константы
  `DecisionEngine`: LTV-обоснование approve/review/reject и `high_mileage`
  (значения-токены — технические идентификаторы, не бизнес-числа: в `rules.php`
  не выносятся). Причина: LTV-код, соответствующий решению; при понижении
  `approve` → `review` пробегом — `high_mileage`. Тем самым ОО-6 (приоритет при
  LTV-`review` + высокий пробег) получает рабочее допущение: причина отражает
  правило, давшее итоговое решение; без понижения остаётся LTV-код. Допущение
  требует подтверждения заказчиком (см. Вопросы).
- Валидация REQ-MILEAGE-03: отличать «пустоту» от нуля — отсутствующий ключ,
  null и пустая строка дают ошибку `mileage` → 422; число `0` остаётся валидным
  пробегом (спека невалидной делает именно отсутствие значения, не ноль).
- Хранение причины — столбец `decisions.decision_reason VARCHAR(32) NULL`
  (nullable: у записей до задачи причины нет — ОО-4, пересчёт не входит; seed
  не трогаем). VARCHAR, не ENUM: коды причин расширяются добавлением правил,
  ENUM требовал бы ALTER на каждую новую причину. Значения-коды контролирует
  PHP (`DecisionEngine`), БД хранит строку как есть.
- Отклонённые альтернативы: проверка пробега в `ApplicationValidator` (там жёсткий
  422, а нужно `review`); в контроллере (бизнес-правило не в HTTP-слое); инлайном
  в `AssessmentService` (расщепляет логику решения между классами); причина как
  массив «объяснений» вместо одного кода (спека требует один код у каждого решения).
- Значение порога в `rules.php` появляется только после закрытия ОО-5
  (согласование риск-менеджментом, AGENTS.md) — см. Шаги, шаг 1, и Вопросы.

## 2. Шаги

1. `rules.php`: секция `mileage.review_from_km` + docblock. Значение — из
   интервью (Вопрос 1, см. spec_MILEAGE REQ-MILEAGE-01). **Блокировка ОО-5:**
   внесение числа в конфиг — только при наличии ссылки на согласование
   риск-менеджмента (тикет); без неё — стоп и вопрос человеку (AGENTS.md).
   До закрытия ОО-5 реализация по этому шагу не стартует: тесты читают порог
   из `rules.php` и без значения невыполнимы.
2. `DecisionEngineTest` (красный): setUp на новую сигнатуру, пороги из rules.php;
   граничный data-provider (порог − 1 / ровно / + 1 с ожидаемой причиной);
   кейсы «только понижает» (LTV-`review`/`reject` + пробег на пороге и выше);
   инвариант `review_from_km <= vehicle.max_mileage_km`. Тесты красные — движок
   пока не умеет.
3. `Decision` + `DecisionEngine` (зелёный): DTO, новые сигнатуры; понижение
   при `mileage >= review_from_km`, причина `high_mileage` только при понижении,
   иначе LTV-код решения; обновить docblock. Юнит-тесты зелёные.
4. `AssessmentService` + `AppFactory` одним шагом: проброс `$input['mileage']`,
  `reason` в результате `assess()`, порог из конфига. Иначе сломаны и сборка
  приложения, и `AssessmentServiceTest`. После шага — контрольный поиск `decide(`
  и `DecisionEngine(`: посторонних вызовов остаться не должно.
5. `AssessmentServiceTest`: сквозные кейсы понижения, обнуления лимита и причины.
6. `ApplicationValidatorTest` (красный) → `ApplicationValidator` (зелёный):
   REQ-MILEAGE-03 — пустая строка → ошибка `mileage`; фиксация REQ-MILEAGE-05 —
   жёсткий потолок не сдвинулся.
7. Причина в HTTP и БД: `ApplicationController` (`reason` в JSON ответов
   `ltv`/`create`), `ApplicationRepository` (INSERT/SELECT `decision_reason`),
   `db/schema.sql` + `db/migrations/add_decision_reason.sql` (ALTER живой БД,
   применить вручную — см. Файлы). Контрольный поиск `approved_limit` и
   `decision` в контроллере/репозитории: причина прокинута во все пути решения.
8. Проверка: `make lint`, `make test`, ручной смоук `POST /api/ltv`:
   пробег «порог − 1» → `approve` с LTV-причиной; «ровно порог» и «порог + 1» →
   `review` с `high_mileage`; пустая строка → 422; пробег за `max_mileage_km` → 422;
   `POST /api/applications` → `GET /api/applications/{id}` содержит причину
   (значения границ — см. spec_MILEAGE, разд. 4).

## 3. Тесты

Граничные значения в тестах берём из rules.php: `review_from_km − 1` / ровно /
`+ 1` — при смене порога тесты следуют за конфигом, а не хранят копии чисел.
Конкретные значения границ и их источники — `docs/spec/spec_MILEAGE.md`, разд. 4.

`tests/Unit/DecisionEngineTest.php` (соответствие AC-MILEAGE-01/02):
- пробег «порог − 1» при LTV-`approve` → `approve`, причина LTV-approve;
- пробег «ровно порог» при LTV-`approve` → `review`, причина `high_mileage`
  (включительная граница — REQ-MILEAGE-01);
- пробег «порог + 1» при LTV-`approve` → `review`, причина `high_mileage`;
- пробег на пороге и выше при LTV-`review` → `review`, причина LTV-review
  (рабочее допущение по ОО-6 — см. Вопросы);
- пробег на пороге и выше при LTV-`reject` → `reject`, причина LTV-reject
  (REQ-MILEAGE-02, не смягчаем);
- существующие LTV-кейсы при пробеге ниже порога — решения и причины не меняются;
- инвариант конфига: `mileage.review_from_km` <= `vehicle.max_mileage_km`, иначе
  правило недостижимо (диапазон между ними перехватывает валидация).

`tests/Unit/AssessmentServiceTest.php` (сквозные, реальные rules.php):
- LTV-`approve` и пробег «порог − 1» → `approve`, причина LTV-approve,
  `approved_limit` равен запрошенной сумме;
- LTV-`approve` и пробег «ровно порог» → `review`, причина `high_mileage`,
  `approved_limit` = 0;
- LTV-`approve` и пробег «порог + 1» → `review`, причина `high_mileage`,
  `approved_limit` = 0.

`tests/Unit/ApplicationValidatorTest.php` (слой валидации — до решения
не доходит; REQ-MILEAGE-03/05):
- ключ `mileage` отсутствует → `ValidationException` с ключом `mileage` в errors;
- `mileage` = null → то же;
- `mileage` = `''` (пустая строка) → то же (регрессия текущего поведения —
  раньше 0, спека требует 422);
- `mileage` = 0 → валидно (спека запрещает пустоту, не ноль);
- пробег `max_mileage_km + 1` → `ValidationException` — жёсткий потолок
  не сдвинулся (AC-MILEAGE-05).

Ручная проверка после `make up` (значения — см. spec_MILEAGE, разд. 4):
- `POST /api/ltv` с пробегом «ровно порог» → `decision: review`,
  `reason: high_mileage`; с «порог − 1» → `approve` с LTV-причиной;
- `POST /api/ltv` с `mileage: ''` → 422 с ключом `mileage` в errors;
- `POST /api/applications` → в ответе `reason`; `GET /api/applications/{id}`
  отдаёт `decision_reason` из БД.

## 4. Риски

1. Два правила о пробеге в разных слоях: жёсткая валидация (422,
   `vehicle.max_mileage_km`) и мягкий порог понижения (`mileage.review_from_km`).
   Зона видимости нового правила — только `review_from_km .. max_mileage_km`.
   Главный риск: порог в rules.php станет больше `max_mileage_km` — правило молча
   станет недостижимым. Защита — инвариант-тест и docblock в rules.php; числа
   дублировать в коде/тестах нельзя.
2. Смена сигнатуры `decide()` и конструктора `DecisionEngine`, плюс новый
   возвращаемый тип `Decision` ломает все точки использования — их ровно четыре,
   все в списке Файлов; менять только согласованно (шаги 2–4). Пропуск = фатальная
   ошибка в рантайме, а не в тестах.
3. REQ-MILEAGE-03 — регрессия текущего поведения: пустая строка сегодня
   становится нулём и может получить `approve`, после задачи — 422. Если
   фронтенд отправляет пустую строку при незаполненном поле, пользователь
   впервые увидит ошибку валидации — это и есть требование спеки (фронтенд
   при этом не меняется: форма уже показывает ошибки 422). Проверить на смоуке.
4. `approved_limit` при понижении обязан остаться 0 — это уже даёт существующая
   строка `AssessmentService.php:39`, её менять не нужно. Риск «доработать» и
   выдать лимит при `review` — не дорабатывать.
5. Живая БД: `schema.sql` применяется только на пустом томе, миграций в проекте
   нет. План вводит каталог `db/migrations/` — новое соглашение, отсутствующее
   в AGENTS.md; ALTER применяется вручную. Риск рассинхронизации: забыть ALTER
   на существующем стенде → `save()` падает на неизвестном столбце. Защита:
   смоук шага 8 с сохранением заявки; `reset_db.sh` для этого не использовать
   (запрещён AGENTS.md).
6. Старые записи и seed остаются без причины (`decision_reason` NULL, ОО-4):
   карточка/список отдают NULL — так и задумано, пересчёт вне скоупа; если
   заказчик потребует заполнить старые — отдельная задача.
7. Число порога: без закрытия ОО-5 значение в `rules.php` не вносится
   (спека REQ-MILEAGE-01, AGENTS.md). Риск: реализация стартует и «застревает»
   на шаге 1 — до согласования не активировать, человеку задать вопрос.
8. ОО-6 — приоритет причины при LTV-`review` + высокий пробег не задан ни
   intent, ни спекой; план берёт допущение «причина = правило, давшее итоговое
   решение» (понижение заменяет причину, без понижения — LTV-код). Если
   заказчик решит иначе — правка локальна (точка замены причины в `decide()`),

9. Коды причин (`ltv_approve` и т.д.) — технические токены, выбранные планом;
   словарь спекой не зафиксирован. Если у заказчика/андеррайтинга есть свой

   (значения видны в API/БД — сменить до того, как их начнут читать).
10. Не входит (out of scope): фронтенд (`app.js` рендерит `decision` как есть,
